# ai-kuse

AI の文章によく出るワードだけを見つけて、言い換えを提案します。ワードの一覧は `${CLAUDE_SKILL_DIR}/terms/*.yaml` にあり、検出は `scripts/check.py` が行います。あなたの仕事は、検出された箇所ごとに文脈を読み、言い換えるか残すかを決めて、言い換えるなら文として自然な案を出すことです。

<!-- ai-kuse-disable -->

## 使い方の種類

引数の最初の単語で決めます。

| 呼び出し | すること |
|---|---|
| `/ai-kuse <ファイル…>` か `/ai-kuse` | 検出して提案する（check）。ファイルは書き換えない |
| `/ai-kuse fix <ファイル…>` | 提案のうち「言い換える」と決めたものをファイルに反映する |
| `/ai-kuse survey <ワード…>` | ワードを足すべきかを調べる。足すときの検出のパターンと重さも決める |
| `/ai-kuse add <ワード> [言い換え…]` | ワードを一覧に登録する（先に survey と同じ調べ方で確かめる） |
| `/ai-kuse list [分類]` | 登録済みのワードを一覧で見せる |

対象の決め方（check と fix）:
1. 引数にファイルがあれば、それを見る。
2. 依頼に文章が貼ってあれば、それを見る（`--stdin` で渡す）。
3. どちらもなければ、直前の自分の返答に、依頼を受けて書いた本文（作業報告ではないもの）があればそれを見る。
4. それもなければ、どのファイルか文章かを尋ねる。

## check: 検出して提案する

1. 検出する。
   ```bash
   uv run --script ${CLAUDE_SKILL_DIR}/scripts/check.py --format json <ファイル…>
   ```
   文章を渡すときは `--stdin` を付け、ヒアドキュメントで本文を渡す。
2. 指摘ごとに、その行と前後2行ほどを読み、次の3つのどれかに決める。
   - **言い換える**: AI の言い回しとして使われていて、言い換えたほうが伝わる。
   - **残す**: 次のどれかに当たる。
     - `keep_when` の場面に当たる
     - `quoted: true`（カギ括弧や引用符の中）で、ほかの文書や人の発言を引いている
     - 正式な名前、画面の項目名、識別子、API の名前の一部
     - プロジェクトや分野で定着している
   - **確かめる**: 言い換えに要る中身（何をまとめるのか、何を指すのか）が原文から分からない。
3. 言い換えの案の作り方。
   - `suggest` の言葉に差し替えるだけで済むなら、そうする。済まないときは、前後の文から中身を読み取って文を書き直す（「寄せる」→ 何をどこにまとめるか）。
   - 原文にない事実、数値、主語、理由を足さない。中身が分からなければ「確かめる」にする。
   - 意味の強さを変えない（「担保する」を「保証する」にすると強くなる、など）。
   - 指摘されたワード以外は変えない。文末や読点の修正は、頼まれない限りしない。
4. 次の形で返す。

   ```
   ## ai-kuse の指摘（N 件: 言い換える X / 残す Y / 確かめる Z）

   | 場所 | 元 | 案 | 判断 | 理由 |
   |---|---|---|---|---|
   | README.md:12 | 設定はこの YAML を正本とする。 | 設定はこの YAML を基準にする。 | 言い換える | 唯一の版という含みが不要 |
   | README.md:30 | 「品質を担保すること」（通達） | そのまま | 残す | 引用 |

   ### 確かめたい点
   - README.md:18「処理を寄せる」: どのモジュールにまとめる意図ですか。
   ```
   - 指摘が0件なら「指摘なし」とだけ書く。
   - 残すと決めたワードがそのプロジェクトで今後も使うものなら、`.ai-kuse/allow.txt` に足せることを1行で添える。

## fix: ファイルに反映する

1. check と同じ手順で判断する。
2. 「言い換える」の箇所だけを Edit で書き換える。「確かめる」は書き換えず、問いとして残す。
3. もう一度 check.py を実行し、書き換えた箇所の指摘が消えたことと、新しい指摘が出ていないことを確かめる。
4. 変えた箇所の一覧（元 → 案）と、確かめたい点を返す。

## survey: ワードを調べる

`${CLAUDE_SKILL_DIR}/references/survey.md` を読み、その手順で調べる。流れは次のとおり。

1. 文章群がなければ、または1か月以上前のものなら作る（`survey.py prepare`）。Qiita API は1時間に60回までなので、取得済みの分は使い回す。
2. `survey.py neighbors` で使い方を直前の言葉ごとに分け、AI に特有の使い方があるかを見る。
3. 除外方式か限定方式かを決めてパターンを書き、`survey.py count` で数える。
4. `survey.py samples` で用例を読む。
5. 結果を返す。数値（10万字あたり、ai / human / recent）、AI と人の用例の違い、根拠の強さ、足すかどうかと重さの案を書く。事実と解釈を分ける。
6. 利用者が足すと決めたら、add の手順に進む。

## add: ワードを登録する

1. 利用者からワードを受け取る。言い換えや理由、分野（既定は tech）、重さが書いてあれば使う。重さは利用者の指定を優先する。
2. 同じワードや同じ id がすでにないかを `terms/*.yaml` で確かめる。あれば、その項目に足すかを尋ねる。
3. まだ調べていなければ、survey の手順 2〜4 で使い方と件数を確かめる。根拠が弱いときは、数値を伝えてから足すかを尋ねる（利用者がすでに足すと決めていれば、そのまま足す）。
4. `references/survey.md` の5章のとおり YAML に書き、6章のとおり確かめる（validate.py、survey.py term、誤検出の文をテストに足す、survey.py evidence --write）。
5. 調べた結果を `research/` の報告に追記する（7章）。
6. 足した項目を見せる。コミットは頼まれたときだけする（リポジトリは `${CLAUDE_SKILL_DIR}` のリンク先）。

## list: 一覧を見せる

`terms/*.yaml` を読み、ワード・分類・重さ・主な言い換えを表にして返す。分類を指定されたら、その分類だけにする。

## プロジェクトごとの除外

対象のファイルがある git リポジトリの最上位に `.ai-kuse/allow.txt` を置くと、そこに書いた id かワードは検出しない（1行に1つ、`#` 以降はコメント）。1行だけ外すには行末に `<!-- ai-kuse-ignore -->`、範囲を外すには `<!-- ai-kuse-disable -->` と `<!-- ai-kuse-enable -->` で囲む。コードブロック、インラインコード、URL はもともと見ない。
